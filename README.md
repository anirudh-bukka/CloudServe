# CloudServe Support Desk

A support ticket triage system for the FDE capstone. It accepts email, live chat, documentation comments, and forum tickets; classifies urgency and intent; retrieves passages from the supplied knowledge base; answers with checked citations when safe; and escalates other cases with a summary and sources. The browser console lets someone explore decisions without creating an account or obtaining an API key.

## Start locally

You need Python 3.10 or newer. No packages, model downloads, or external accounts are required.

```bash
git clone https://github.com/anirudh-bukka/CloudServe.git
cd CloudServe
python3 -m src.api
```

Open [http://localhost:8000](http://localhost:8000). Choose a sample ticket, select **Analyze ticket**, and inspect its route and evidence. The themed system status page is at `/status`; the machine-readable health endpoint remains at `/api/health`.

To use a different port: `PORT=8080 python3 -m src.api`. The service binds to all interfaces by default. For a network you do not control, use the deployment instructions below rather than exposing your laptop directly.

## Run the full validation set

```bash
python3 -m evaluation.harness --input data/validation_tickets.json --output evaluation/results
```

The command writes `decisions.json`, `metrics.json`, and `decisions.sqlite3` to the output directory. It accepts **any JSON array of tickets with the same schema**, including an unseen file. Malformed individual tickets are escalated and logged; one bad record does not stop the run. To choose the database path explicitly, add `--db path/to/decisions.sqlite3`. Repeated runs receive distinct run IDs in the log.

To inspect a result quickly:

```bash
python3 -m json.tool evaluation/results/metrics.json
```

## Run the tests

```bash
python3 -m unittest discover -s tests -v
```

The suite covers all four channels, answer citations, deterministic routing, a no-hit retrieval case, prompt injection and private data blocks, and decision log reconciliation.

## HTTP API

```bash
curl -X POST http://localhost:8000/api/triage \
  -H 'Content-Type: application/json' \
  -d '{"ticket_id":"DEMO-1","channel":"email","subject":"API key returning 401","body":"One production key stopped working, while our other keys still work."}'
```

`GET /api/samples` lists sample tickets and `GET /api/samples/VAL-0001` returns one. `POST /api/triage` returns the class, urgency, confidence, route, reason, answer or summary, retrieved passages, checks, and latency. Each request is logged in SQLite.

## Make it available to others

The repository includes a `Dockerfile` and `render.yaml`. After pushing this repository to GitHub, create a [Render Blueprint](https://dashboard.render.com/blueprints) from the repository. Render reads `render.yaml`, builds the Docker image, and gives you a public HTTPS URL. Visit that URL to use the browser console. The health check is `/api/health`. Render's free filesystem is ephemeral; run the batch harness locally or attach persistent storage if the decision log must survive redeploys. This public demo is intended for synthetic capstone tickets, not live customer records.

For any Docker host:

```bash
docker build -t cloudserve .
docker run --rm -p 8000:8000 cloudserve
```

If automatic answers need to stop immediately, set `AUTO_RESPONSE_ENABLED=false` in the running environment and restart the process. The service then escalates all incoming tickets. Other optional settings are documented in `.env.example`; no `.env` file is necessary. Environment variables are read directly, so a `.env` file is only a reference unless your host loads it.

## Design and evidence

The app uses local weighted nearest-neighbor classification trained on the supplied 500 development tickets, TF-IDF cosine passage retrieval over the 29 supplied articles, and extractive answer drafting. It has no external model dependency. This makes the full batch run free, deterministic, and resilient to provider outages or rate limits. Confidence is mapped to observed accuracy on a grouped development holdout; its calibration is reported on validation tickets and needs more evidence before production use. Ambiguous historical routes are escalated. See [architecture](docs/architecture.md) for the order of safety checks and limitations.

The bundled 80 validation tickets are demonstration and evaluation inputs. This repository includes no hidden assessment tickets. The current measured results are generated by the harness when run; see `evaluation/results/metrics.json` after a run. `projected_first_contact_resolution` is explicitly a projection, since no post-answer customer outcome has been observed. Processing latency is not customer reply delivery time.

The supplied `development_tickets.json`, `validation_tickets.json`, and `documentation.json` originate from the FDE capstone pack. The application code and prose were drafted with AI assistance and reviewed through executable tests. The public [reference project](https://github.com/omiiii21/FDE-Capstone) was read for context; this implementation uses its own architecture, standard-library runtime, and user interface rather than copying its code.
